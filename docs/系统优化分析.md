# Theia 系统优化分析

> 分析日期：2026-02-28
> 覆盖范围：agent、server、video、web 全栈

---

## 一、架构与模块化

### 当前优点

- LangGraph StateGraph 提供清晰的流水线编排，10 个节点线性推进
- 子模块化重构（extraction/llm/output/parsing/quality）有效分离关注点
- `ProgressCallback` 协议实现 agent 与 server 解耦
- 多 Agent 脚本生成架构（Story Architect → Scene Writer → Visual Director → Pacing Reviewer）职责清晰

### 优化方向

#### 1.1 质量门控应独立为 LangGraph 节点

当前 `quality_gate` 嵌入在 `extract_node` 内部，代码中虽定义了 `quality_gate_node` 但未接入图。应将其作为独立节点插入 `extract_node` 之后：

- 交互模式下可在门控后暂停审核
- 门控可独立重试而无需重新提取
- 状态流更清晰

#### 1.2 消除循环导入

`gate.py` 从 `pipeline` 导入 `_make_on_token`，形成循环依赖。应通过依赖注入传递回调。

#### 1.3 清理遗留代码

| 遗留项 | 说明 |
|--------|------|
| `PipelineContext` | 与 `PipelineState` 功能重叠，应合并或移除 |
| `route_tts_or_skip` | 已定义但未使用（TTS 跳过逻辑在节点内处理） |
| `schemas_compat.py` | 兼容层应设置迁移完成后的清理计划 |

#### 1.4 减少 JSON 序列化/反序列化

`paper_summary_json` 和 `video_script_json` 以字符串形式存储在 state 中，每个节点都需要解析和重新序列化。可考虑使用结构化对象或 LangGraph 的序列化支持。

## 二、性能优化

### Agent 侧

#### 2.1 并行化场景写作

当前 Scene Writer 按顺序为每个场景生成旁白。场景之间有全局 blueprint 作为上下文但互相独立，可以并行调用 LLM：

```python
with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(write_single_scene, plan, summary) for plan in blueprint.scenes]
    narrations = [f.result() for f in futures]
```

预期收益：10 个场景从串行 ~50s 降至 ~15s。

#### 2.2 分块提取并行化

chunked extraction 目前逐段串行处理，对独立章节可并行提取。

#### 2.3 Visual Director 调用去重

scriptwriter 中调用一次（用估算时长），`visual_director_node` 中带真实 `word_timings` 又调用一次。应统一接口，避免重复计算。

#### 2.4 质量门控并行修复

`field_completeness`、`grounding`、`entity_match`、`section_coverage` 互不依赖的维度可以并行修复。

### Video 侧

#### 2.5 渲染热路径 Memoize

以下操作在每一帧都重新执行，是主要性能瓶颈：

| 组件 | 问题 | 方案 |
|------|------|------|
| `FormulaScene` | 每帧调用 `renderKatex()` | `useMemo` 按公式字符串缓存 |
| `FormulaOverlay` | 每帧调用 `renderKatex()` | 同上 |
| `InlineLatex` | 每帧执行 `parseLatexSegments()` + `renderInlineKatex()` | `useMemo` 按 text 缓存 |
| `HighlightText` | 每帧创建 `new RegExp()` + `text.split()` | `useMemo` 按 text/highlights 缓存 |
| `Subtitle` | 每帧重新计算行分组 | `useMemo` 按 wordTimings 缓存 |

#### 2.6 KaTeX 逻辑统一

KaTeX 渲染在 `FormulaScene`、`FormulaOverlay`、`MethodScene`、`InlineLatex` 中各有一份 `cleanLatex`/`renderKatex`。应抽取为 `utils/katex.ts` 共享工具。

#### 2.7 useChoreography 优化

`phases.find()` 和累积 `Set` 迭代在每帧运行。大量 phases 时可优化为二分查找或预计算查找表。

## 三、可靠性与容错

### 3.1 LLM 调用降级路径

| 问题 | 影响 | 建议 |
|------|------|------|
| `_try_fallback` 绕过速率限制 | API 故障时可能雪崩 | fallback 调用也走 `_throttle` |
| 无熔断器 | 持续失败的 API 仍被反复调用 | 引入 Circuit Breaker 模式 |
| litellm 路径无超时 | 请求可能无限等待 | 设置统一超时（如 120s） |
| 双重重试（`robust_completion` 3 次 + extraction 自身重试） | 最多 9 次重试 | 统一重试策略 |

### 3.2 SSE 连接可靠性

| 问题 | 影响 | 建议 |
|------|------|------|
| 客户端 `onerror` 仅关闭连接 | 网络抖动导致进度丢失 | 添加指数退避重连 |
| 无心跳/keepalive | 连接可能静默断开 | 服务端定期发送心跳事件 |
| 队列满时事件被丢弃 | 进度信息丢失 | 增大队列或实现持久化 |
| 无 `Last-Event-ID` | 断线后无法恢复 | 支持 event ID 断点续传 |

### 3.3 Video 渲染容错

| 问题 | 建议 |
|------|------|
| 无 `ErrorBoundary` | 每个场景外包裹 ErrorBoundary |
| 图片加载失败无处理 | FigureScene 添加占位符 |
| Manim 视频加载失败无处理 | ManimClipPlayer 添加 fallback |

### 3.4 交互状态持久化

LangGraph 交互模式的状态仅在 TaskManager 内存中，服务重启即丢失。应持久化到 SQLite 或文件系统。

## 四、Token 效率与成本

### 4.1 上下文传递冗余

- 完整 `PaperSummary` 被发送给 Story Architect 和 Scene Writer，但每个 Agent 只需其中一部分
- Scene Writer 一次性接收所有场景的 blueprint + 完整 summary，上下文很大

建议：为每个 Agent 构建精简上下文，Scene Writer 按场景拆分调用。

### 4.2 提示词缓存

多次调用使用相同的 system prompt（extraction_pass2、scene_writer 等）。支持 prompt caching 的 API（如 Anthropic）可显著减少 token 消耗。

### 4.3 统一重试策略

`robust_completion` 内置 `max_retries=3`，extraction passes 又有自己的重试逻辑。应在一个层面统一管理重试。

## 五、类型安全与数据一致性

### 5.1 Python ↔ TypeScript Schema 同步

当前 Pydantic 模型和 Zod schema 手动维护，容易不同步。建议：

- 方案 A：从 Pydantic 模型生成 JSON Schema → 生成 Zod 类型
- 方案 B：使用 OpenAPI spec 作为 single source of truth
- 方案 C：CI 中添加 schema 一致性检查

### 5.2 Video 侧缺少运行时校验

Zod schema 已定义但从未调用 `.parse()` / `.safeParse()`。Python 端传入的 JSON 可能不符合 schema，直接到达组件导致运行时错误。应在 `PaperVideo` 或 `Root` 入口处验证。

### 5.3 场景 data 缺少类型判别

`Scene.data` 类型是 `Record<string, unknown>`，场景组件通过 `as unknown as TitleData` 强转。应改为 discriminated union：

```typescript
type SceneData =
  | { type: "title"; data: TitleData }
  | { type: "formula"; data: FormulaData }
  | ...
```

### 5.4 前后端 API 类型不同步

| 问题 | 建议 |
|------|------|
| `getTaskScript` / `getTaskSummary` 返回 `any` | 添加具体类型 |
| `TaskConfig` 前后端字段不一致 | 引入 OpenAPI codegen |
| `UserSettingResponse.value` 前后端类型不同 | 统一为 JSON |

## 六、安全

| 问题 | 严重性 | 建议 |
|------|--------|------|
| CORS `allow_origins=["*"]` + `allow_credentials=True` | **高** | 生产环境限制 origin 列表 |
| 无认证/授权 | **高** | 添加 API Key 或 JWT 认证 |
| URL 抓取 SSRF 风险 | **中** | 校验 URL 白名单，禁止内网地址（`127.0.0.1`、`10.*`、`192.168.*`） |
| 无速率限制 | **中** | 添加请求频率限制（如 slowapi） |
| 数据库迁移错误被 `except: pass` 静默吞掉 | **中** | 记录日志，使用 Alembic 版本化迁移 |
| 文件上传仅检查扩展名和大小 | **低** | 可考虑 magic bytes 深度校验 |

## 七、可扩展性

### 7.1 单进程 + SQLite 限制

当前架构不支持水平扩展。多实例部署需要：

| 组件 | 当前 | 目标 |
|------|------|------|
| 数据库 | SQLite | PostgreSQL |
| 任务队列 | 内存线程 | Redis + Celery |
| SSE 状态 | 内存 Queue | Redis pub/sub |
| 交互状态 | 内存 | 数据库持久化 |

### 7.2 场景扩展缺少插件机制

添加新场景类型需要修改多处：

1. `SceneType` enum（Python + TypeScript）
2. Scene 组件（TSX）
3. `sceneComponentMap`（PaperVideo.tsx）
4. `scene_registry.py`（Python）
5. Prompts

考虑自动发现机制或统一的场景注册 API。

### 7.3 缺少基础设施端点

| 端点 | 用途 |
|------|------|
| `GET /health` | 健康检查（容器化部署） |
| `GET /ready` | 就绪检查（数据库连接等） |
| `GET /metrics` | Prometheus 指标 |

## 八、代码质量与重复

### 8.1 重复的中文检测逻辑

`_chinese_ratio` 在 `scene_writer.py`、`scriptwriter.py` 中各有一份，`_CJK_RE`/`_CJK_RANGES` 也有重复定义。应统一到 `_utils.py`。

### 8.2 章节解析重复

| 函数 | 位置 | 功能 |
|------|------|------|
| `split_sections_with_labels` | llm/config.py | 语义章节标签 |
| `_sections_from_content_list` | extraction/synthesize.py | content_list 章节分割 |
| `_classify_section` | llm/config.py | 章节分类 |

这些函数功能重叠，应统一为一个章节解析模块。

### 8.3 LLM 调用模式重复

extraction、gate、scriptwriter 都有相同的模式："构建 kwargs → 调用 robust_completion → 解析 JSON"。可抽取为：

```python
async def llm_json_call(prompt: str, schema: type[BaseModel], model: str, **kwargs) -> BaseModel:
    ...
```

### 8.4 API Key 解析重复

每个节点都做 `state.get("X_api_key") or state.get("Y_api_key")` 的链式解析。应集中到 `LLMConfig` 中。

### 8.5 Video 组件硬编码

| 位置 | 问题 |
|------|------|
| `OverviewScene` | 硬编码高亮词：`["注意力", "Transformer", "attention", ...]` |
| `MethodScene` | 硬编码标签 "方法论" |
| `PaperVideo` | 两个硬编码 Composition（PaperVideo, PopsciVideo） |

## 九、开发体验与工程化

### 9.1 测试覆盖

当前无测试文件。建议按优先级添加：

| 优先级 | 测试类型 | 覆盖范围 |
|--------|----------|----------|
| P0 | Schema 验证 | Pydantic 模型 + Zod schema 一致性 |
| P0 | 提取单元测试 | Mock LLM 响应，验证提取逻辑 |
| P1 | Pipeline 集成测试 | 使用 fixture 跑完整流水线 |
| P1 | API 端点测试 | FastAPI TestClient |
| P2 | Video Zod 校验 | 验证 Python 输出能通过 Zod parse |

### 9.2 CI/CD 配置

建议添加 GitHub Actions：

```yaml
- lint: ruff check + ruff format --check
- type-check: vue-tsc (web) + mypy (agent/server)
- test: pytest (agent/server)
- schema-check: 验证 Python/TypeScript schema 一致
```

### 9.3 日志与可观测性

| 问题 | 建议 |
|------|------|
| 无结构化日志 | 使用 structlog 或 JSON formatter |
| 无请求追踪 | 添加 request ID 中间件 |
| 无 LLM 调用度量 | 记录每次调用的 model、tokens、latency、cost |
| 无服务端请求日志 | FastAPI 中间件记录请求/响应 |

## 十、用户体验优化

### 10.1 渐进式反馈

当前只有阶段级别的进度（parsing 10%、extracting 30% 等）。可在每个阶段内提供更细粒度的进度：

| 阶段 | 细粒度进度 |
|------|-----------|
| 提取 | 已处理 3/8 章节 |
| 脚本 | 已生成 5/12 场景旁白 |
| TTS | 已合成 7/12 场景语音 |
| 渲染 | 已渲染 60% 帧 |

### 10.2 预估时间

基于历史任务数据（论文长度、图片数量 → 处理时间），提供预估剩余时间。

### 10.3 离线容错

前端在网络断开后应缓存当前状态，恢复后自动重连 SSE 并同步。

### 10.4 错误信息可读性

当 LLM 调用失败时，向用户展示友好的错误信息而非原始异常，并提供"重试"或"更换模型"的操作选项。
